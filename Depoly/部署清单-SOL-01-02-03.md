## 0. 三条 finding 要解决什么，一句话回顾

- **SOL-01**：初始代币全归部署者 → 用多签持有未分发代币 + 公开分发计划。
- **SOL-02**：`EscrowVault` 的 admin/operator/guardian 三个角色都是单地址 EOA，私钥泄露即灾难 → 迁移到多签/Timelock。
- **SOL-03**：合约升级权（`_authorizeUpgrade`）挂在 `DEFAULT_ADMIN_ROLE` 上，和 SOL-02 是同一把钥匙 → 随 admin 一并迁移，共享关闭条件。

**关键原则（此前已定，写在这里提醒）**：只有 `DEFAULT_ADMIN_ROLE` 进 48h Timelock。`OPERATOR_ROLE`（结算/发 root，高频操作）和 `GUARDIAN_ROLE`（`pause`/`cancelPendingRoot`，应急刹车）都**不进 Timelock**，否则 Guardian 关键时刻也要等 48 小时，等于拆了唯一的快速刹车。

> **一个容易混的点，说清楚**：Guardian **日常执行**`pause()`/`cancelPendingRoot()`不受 admin 治理方式影响——这两个函数是 `onlyRole(GUARDIAN_ROLE)`，跟 admin 在哪没关系，永远是快的。会进 Timelock 延迟的，只是"**更换**Guardian 是谁"这个动作（`updateGuardian` 是 `onlyRole(DEFAULT_ADMIN_ROLE)`）——而这本来就该慎重、不该秒批，所以合理。

## 1. 需要准备的多签（先于合约部署/迁移前确定人选）

| 用途 | 建议阈值 | 说明 |
|---|---|---|
| **Admin 多签**（Timelock 的 proposer/executor） | 团队 5 人及以上用 3/5；人少则 2/3 | 最高权限，见下方"全内部签名人"披露 |
| **Guardian 多签** | 2/3 或 3/5，签名人**尽量在线、能快速响应** | 独立于 Admin 多签，人选应包含 7x24 值守的运营/安全同学，追求速度不追求人数；**全内部完全没问题**，本来就该是自己的值班同学 |
| **Operator** | 视运营节奏：热钱包（自动化结算）或轻量 2/3 多签 | 高频操作，不建议接入需要人工签名审批流程较慢的多签工具 |
| **代币托管多签**（SOL-01，若生产用自有代币） | 3/5 | 持有未分发的代币供应；若生产直接用 USDT/USDC，此项可跳过 |

**行动项**：负责人先确定以上每类的签名人名单（钱包地址），交给 DevOps 用 Gnosis Safe 创建。**这一步必须先做**，后面所有脚本都需要这些地址作为输入——部署 Safe、调用 `initialize()`，都要真实地址，不存在先占位以后改的空转步骤。

> **测试链也要给具体地址，但不需要是主网正式版**。建议：找**真实打算参与的内部同事**（哪怕只是当前的初步人选），每人用软件钱包建一个测试链地址（几分钟的事，不用硬件钱包，测试链的钱不值钱）。这样部署演练的同时，团队也把"怎么在 Gnosis Safe 上审批"这个操作流程练熟了——如果用程序员随手生成的陌生地址，只能验证代码机制，验证不了团队会不会用。人选以后能通过 `updateOperator`/`updateGuardian` 调整，不是不可逆的决定。Operator 只需要 1 个地址（非多签），随便指定即可。

### ⚠️ 关于"目前签名人都是项目方内部"，必须说清楚的残余风险

多签防的是**单点私钥泄露**（一个人电脑中毒/丢设备，不会导致资金被盗）。但它**防不住内部串通或被整体施压**——如果 3/5 或 2/3 的签名人全是团队内部、甚至常在同一间办公室，理论上"3 个人一起被说服/胁迫/离职后勾结"跟单一 admin 的风险性质是类似的，只是操作上麻烦一点。这不是要阻止你现在这么做（早期阶段完全合理、CertiK 也不会因此卡关），而是要如实认识到：**这是"降低单点故障"而不是"消除中心化"**，两者对 CertiK 和潜在投资人说法应该不同。

**现阶段（全内部签名人）建议的最低卫生标准**（不做这些，多签就只是形式）：
- 每个签名人用**自己的**设备/钱包，不共享私钥、不放在公司共享盘或聊天工具里传。
- 尽量覆盖不同的人（不要为了图快让 1 个人用 3 个不同地址凑够阈值——那和单签没有本质区别）。
- 测试链阶段用软件钱包/热钱包即可；**主网正式上线前**，Admin 多签的私钥建议换成硬件钱包保管。

**中长期**：之前给 CertiK 的整改回复里已经写了"v3.0 引入 DAO/治理"的路线图，实际执行时可以更早一步——在主网上线前，Admin 多签**引入至少 1 名项目团队之外的独立第三方**（投资方代表、独立顾问均可），这是把"降低单点故障"升级为"真正降低中心化"最低成本的一步。这一步不阻塞测试链部署，留作主网前的行动项即可。

## 2. Admin 角色迁移到 Timelock + 多签（SOL-02/03 核心）

### 2.1 路径已锁定：路径 B（全新部署，直接就位）

Base 测试链、还没上主网，没有历史状态要迁移，所以直接走**主网也会用的同一套干净路径**：先部署 Timelock+Safe，再让 `EscrowVault.initialize()` 的 `initialAdmin` 参数直接填 Timelock 地址——EOA 从来没拿过 admin，没有"过渡期同时持有"的风险窗口。§2.2 保留路径 A 的说明（`deploy_governance.py` 现成脚本对应的场景）仅作参考，**当前不需要执行**；直接看 §2.3。

> 测试链上的小技巧：`TIMELOCK_DELAY` 不必用主网的 172800 秒（48h），可以先设成一个短值（比如 600 秒 = 10 分钟）方便测试迭代——但**流程本身**（部署 Timelock → `initialize` 填 Timelock 地址 → 验证角色）要跟主网完全一样，这样测试链才是真正的主网演练，不是走另一套路子。**主网部署前务必把这个参数换回 172800**，别忘了改回去。

### 2.2 路径 A 的施工步骤（迁移现有部署，当前不需要，留作参考）

1. 确保 `contracts/Governance.sol` 已随合约一起 `forge build`（生成 `TimelockController` 的编译产物，脚本靠这个部署 Timelock）。
2. 配置环境变量：
   ```bash
   export RPC_URL="https://bsc-dataseed1.binance.org/"      # 主网；测试先用测试网 RPC
   export DEPLOYER_PRIVATE_KEY="0x..."                       # 当前持有 DEFAULT_ADMIN_ROLE 的 EOA 私钥
   export ESCROW_PROXY_ADDRESS="0x..."                       # 已部署的 EscrowVault 代理地址
   export GNOSIS_SAFE_ADDRESS="0x..."                        # §1 中"Admin 多签"的 Gnosis Safe 地址（必须已创建）
   export TIMELOCK_DELAY="172800"                            # 48h，默认即此值，不需要改
   ```
3. **⚠️ 私钥安全提示**：`DEPLOYER_PRIVATE_KEY` 是明文环境变量，脚本跑完后这个 EOA 的 admin 权限会被自动撤销（Step 3），但**运行期间**这个私钥经手过终端环境，建议：
   - 用一个**只做这一次部署、不装其他资产/权限**的临时钱包；
   - 脚本跑完立刻检查 Step 3/4 的输出确认已撤销，然后这个私钥可以视为废弃，不要再用于任何用途；
   - 不要把这个私钥留在 shell 历史 / CI 日志里。
4. 运行 `python scripts/deploy_governance.py`，脚本会依次：① 部署 TimelockController（48h，proposer/executor 都是 Admin 多签）→ ② 把 `DEFAULT_ADMIN_ROLE` 授予 Timelock → ③ 撤销部署者 EOA 的 admin → ④ Timelock 自己的临时 admin 也 renounce 掉。**这四步是连续执行的，中间不要打断**；如果中途失败，先看链上实际状态再决定要不要重跑（脚本不是"幂等"的，重跑会重新部署一个新 Timelock，可能留下废弃实例）。
5. 脚本最后会打印验证结果 + 生成 `governance_deployment.json`，把里面的 Timelock 地址、Safe 地址存档。

### 2.3 路径 B 的施工步骤（全新部署，推荐）

1. 先用 Gnosis Safe 创建好 Admin 多签（§1）。
2. 单独部署 `TimelockController(48h, proposers=[Safe], executors=[Safe], admin=部署者临时地址)`（可以复用脚本里 Step 1 的部署逻辑单独跑，或让程序员抽出一个独立脚本）。
3. 部署完 Timelock 后，`renounceRole` 掉部署者在 Timelock 上的临时 admin（对应脚本 Step 4 的逻辑）。
4. 部署 `EscrowVault` 代理时，`initialize(initialAdmin, initialOperator, initialGuardian)` 的 `initialAdmin` **直接填 Timelock 地址**（`initialOperator`/`initialGuardian` 见第 3 节，此时可以一步到位填最终地址）。
5. 完成，admin 角色从第一笔交易起就在 Timelock 手上，没有中间状态。

### 2.4 一个脚本本身的小疑点（部署前请程序员确认一次）

脚本导入了 `CANCELLER_ROLE` 常量但从未在代码里主动授予任何人。**这大概率不是问题**——OpenZeppelin 较新版本的 `TimelockController` 构造函数会自动把 `CANCELLER_ROLE` 一并授予每个 proposer，也就是 Admin 多签本身默认就有取消权。但请程序员在部署后**用 `hasRole(CANCELLER_ROLE, GnosisSafeAddress)` 实际查一次**，确认多签确实能取消一个已排队但发现有问题的提案——这是 Timelock 体系里"发现问题能刹车"的最后一道保险，务必核实而不是假设。

### 2.5 换链到 Base 的技术影响（BSC → Base，务必处理）

审计报告原文写的 Ecosystem 是"Binance Smart Chain (BSC)"，实际部署目标变成了 Base（测试链），这件事牵动两处：

1. **SOL-06 的时间参数已重新核算（实测，非估算）**。合约里 `ENTROPY_BLOCK_DELAY=10` 块、`blockhash` 256 块可用窗口，这两个数字本身是任何 EVM 链都一样的"块数"，但它们对应的**墙钟时间**取决于出块速度。

   **实测方法**：直接查询 Base Sepolia 官方公共 RPC（`https://sepolia.base.org`）的 `eth_getBlockByNumber`，取最新区块与往前 5,000 块、50,000 块两个不同跨度的时间戳算差值，交叉验证。

   **实测结果**：两次跨度算出的平均出块时间**完全一致，均为 2.0 秒/块**（精确值，非估算）。

   | 参数 | 区块数 | Base Sepolia 实测（2.0s/块） | 原文档按 BSC 估的（~3s/块） |
   |---|---|---|---|
   | `ENTROPY_BLOCK_DELAY`（锁名单后等几块才能取熵） | 10 块 | **20 秒** | ~30 秒 |
   | `blockhash` 可用窗口（`settleTask` 必须在此内完成） | 256 块 | **约 512 秒 ≈ 8 分 32 秒** | ~13 分钟 |

   Base 上留给 Operator 完成结算的窗口比 BSC **短了约 35%**（8.5 分钟 vs 13 分钟），需要：
   - 把 `docs/security_model.md` 里 SOL-06 SOP 章节"~13 分钟"改成"Base 上约 8.5 分钟（2026-07 实测 2.0s/块）"；
   - 链下监控/告警阈值按新窗口收紧：原计划"结算截止前 5 分钟报警"在 8.5 分钟窗口里占比过高，建议缩短到 2~3 分钟提前量，或做成"取熵区块产生后立即自动触发结算"，不留人工反应时间。
   - 这不是阻塞项（合约逻辑本身不用改，`blockhash`/`block.number` 语义不变），只是运营 SOP 的数字要更新，别用旧的 BSC 估算写进给 CertiK 的文档里。
   - **主网上线前请重新实测一次**：以上是 Base **Sepolia 测试网**当前的实测值，主网出块参数理论上一致（同为 OP Stack，官方目标也是 2 秒/块），但正式上线前建议对 Base 主网再跑一次同样的实测确认，不要直接复用测试网数字。
2. **知会 CertiK**。链换了之后，交付关闭材料时（TimelockController 地址、Gnosis Safe 地址）都会是 Base 浏览器（Basescan）上的链接而不是 BscScan，且这本身是审计范围之外的变化，建议在提交材料时主动说明一句"部署目标链由 BSC 调整为 Base"，避免审计方后续核验时发现链不对而产生疑问。

## 3. Operator / Guardian 多签配置（SOL-02 的另一半，脚本没覆盖）

`deploy_governance.py` **只处理 admin**，完全没碰 `OPERATOR_ROLE` / `GUARDIAN_ROLE`。这两个角色要单独配置，而且**时机有讲究**：

- **如果走路径 B（全新部署）**：最省事——`initialize()` 一次性把 `initialOperator`/`initialGuardian` 填成最终的 Operator 钥匙 / Guardian 多签地址，完全不需要后续 `updateOperator`/`updateGuardian` 调用。
- **如果走路径 A（已部署、需要换成多签）**：必须**在 admin 还是部署者 EOA 的时候**（也就是在第 2 节的迁移脚本跑之前），先用部署者身份调用一次：
  ```
  updateOperator(旧Operator地址, 新Operator多签/热钱包地址)
  updateGuardian(旧Guardian地址, 新Guardian多签地址)
  ```
  这两个函数是 `onlyRole(DEFAULT_ADMIN_ROLE)`。一旦 admin 迁移到 Timelock 之后再想换 Operator/Guardian，就要走 48h 审批——初次搭建阶段没必要为这个等 48 小时，所以**顺序上务必先配置好 Operator/Guardian，再迁移 admin**。

**行动项**：DevOps 先确定 Operator 和 Guardian 的最终地址（§1 表格），再决定走哪条路径、在哪一步把它们填进去。

## 6. 验收（组长在提交 CertiK 前会复核的点）

1. `hasRole(DEFAULT_ADMIN_ROLE, TimelockAddress)` 为 true；原 EOA 为 false。
2. `hasRole(CANCELLER_ROLE, AdminSafeAddress)` 为 true（见 §2.4）。
3. TimelockController 自身的 `DEFAULT_ADMIN_ROLE`（即 Timelock 的"管理员的管理员"）应为空——已被 renounce，任何角色变更需通过 Timelock 自身的 propose→wait 48h→execute 流程，不存在旁路。
4. `hasRole(OPERATOR_ROLE, ...)` / `hasRole(GUARDIAN_ROLE, ...)` 指向的是各自最终的多签/钥匙地址，不再是初始部署 EOA。
5. 用一次"真实的小额升级提案"跑通 Timelock 全流程（propose → 等 48h 或测试网调快时间 → execute），确认 48h 延迟真实生效，不是配置上写了但没测过。
